# Card redesign — PIPELINE

How the card chrome is built and coloured now. Supersedes the "recreate chrome in SVG" plan (archived;
see the warning lesson in `STATUS.md`). Read with `BRIEF.md`, `LAYERS.md`, `PIECES.md`.

---

## The direction (Noodle, 2026-09-17)

Chrome is **authored as back/front raster pieces**, then coloured at runtime by **supertype** (not
owner). Hand-recreating the painterly chrome in SVG/CSS was tried and abandoned. The raster split
gives exact authored shapes; a duotone gives one consistent colour per supertype; the gold parts sit
on the `front` pieces and stay gold.

## Pieces (raster, pre-spaced 1176×1500 unless noted)

Authored by Noodle in `_source/cards/`, copied to `_source/cardsGrok/` (originals left in place):

| Piece | Holds | Tinted? |
|---|---|---|
| `newribbon_back` | ribbon cloth | yes |
| `newribbon_front` | gold ribbon trim | no |
| `newicon_back` | winged emblem (blue wings; its gold is covered by `newicon_front`) | yes |
| `newicon_front` | gold crest overlay | no |
| `newicon_priest` / `_knight` / `_lancer` | class glyph (cross / sword / bolt) | no |
| `newring_cost_back` | cost coin blue well | yes |
| `newring_cost_front` | cost coin gold rim + studs | no |
| `newring_owner_back` | owner coin blue well | yes |
| `newring_owner_front` | owner coin gold rim | no |

Rings are loose sprites (cost 300×300, owner 250×250). Ring splits are generated by
`overlays/splits/make-ring-splits.py` (radial well-vs-metal split, source colours preserved).

Border and owner plate are still the **source rasters** (`border_blue`, `bg_priest_blue`) and are
tinted by the same filter as the back pieces.

## Tinting (supertype)

A duotone converts luminance → a dark..light ramp of the target colour, so every asset lands on the
same supertype colour **regardless of its own base hue** (this is why `hue-rotate` failed: it shifted
each asset by its own base). Filters live in the hidden `<svg id="tintDefs">` in the bench; the bench's
`SUPERTYPE` table maps a type to its filter. Applied via `.cardStage.new-chrome` to
`.newBack`, `.cardBorder > img.full`, `.cardBg > img.full`.

| Supertype | Colour | Filter |
|---|---|---|
| Damage | red | `#tintDamage` |
| Support | blue = default asset | none |
| Negative | dark purple | `#tintNegative` |
| Lewd | pink | `#tintLewd` (4-stop; brightens mid-tones — see note) |
| Passive | green | `#tintPassive` |
| Random | white/grey | `#tintRandom` |

**Duotone tuning note.** A narrow ramp keeps the shade but washes out detail; a wide ramp restores
detail but drags mid-tones purple. Lewd uses a 4-stop ramp so the bulk stays bright pink while the
shadows go deep rose. The knobs are the `feFunc*` `tableValues` rows.

## Bench behaviour

- Composer checkbox **`new split chrome`** swaps the source ribbon/icon/cost/owner rasters for the
  split pieces (`.newPiece`), source assembly stays one click away. Hide/show uses `!important` —
  `.cardStage .layer > img.full { display:block }` out-specifies a plain hide rule.
- **`supertype`** select sets `--typeFilter`.
- The new icon is scaled `0.85` (bottom-centre); it is wider/taller than the old medallion and would
  otherwise reach into the tag band.
- **Settings persist across refresh** via `localStorage` (`cardRedesignBench.v1`); saving is gated
  until after restore so init cannot overwrite stored values.

## Multi-type gradient (planned detour, approved)

A card with several supertypes must **shade from one type colour into the next** (red/blue/pink for
DAMAGE · SUPPORT · LEWD), the way the live `.hcCardFrameBlend` does.

Decision: **bake each recolourable PIECE separately** — `cardsGrok/tint/<type>/<piece>.png` for the 6
tintable pieces (border, plate, ribbon back, icon back, and the two ring backs), 5 types (support =
originals). A combined single-layer bake was tried and **rejected**: it breaks vertical (different
hole/frame geometry), needs a re-bake for any change, and kills effects meant to pass **between**
layers (petals under the frame, glints behind the ribbon). Per-piece keeps every layer separate.
Bake script: `overlays/splits/bake-supertype-tints.py` (duotone replicated in PIL, matching
`#tintDefs`).

An N-type card shades by **stacking N copies of each tinted piece**; copy `i` is masked with a 135°
diagonal `linear-gradient(135deg, transparent (share_i - soft), #000 (share_i + soft))`,
`share_i = i/N`, `soft` ~12% — primary leads top-left, last type bottom-right, soft crossover between
each pair. Copies sit at their piece's own z-level, so order and between-layer effects are preserved.

**Status: implemented and working in the bench** (three supertype selects; evidence
`overlays/step6/grad-damage-lewd.png`, `grad-damage-support-lewd.png`).

Two implementation rules learned the hard way:

1. **Mask a wrapper `<span>`, never the `<img>`.** Each copy is
   `<span class="tintWrap" data-piece data-copy><img></span>`; the 135° `linear-gradient` mask goes on
   the span (`tintStack()` in the bench).
2. **Hide unused copies with `setProperty("display","none","important")`.** `.newPiece` carries
   `display:block !important`, which out-specifies a plain inline `display:none`; when copy 2 stayed
   rendered with an `<img>` that had no `src`, Chrome drew its box outline as a faint rectangle on the
   loose coins. That box — not the mask — was the "square edge" artifact. Remove the property when the
   copy is used.

The runtime `#tintDefs` filters are now superseded by the baked variants.

## Live wiring (session 23)

The chrome is wired into the game for **horizontal cards**. Pieces are published as `.webp` by
`overlays/splits/publish-live-chrome.py` into `v13 spire images/cards/chrome/` (same stems as the
source; tint folders under `cards/chrome/tint/<type>/`), so `honeycomb.image()` addresses them by stem.

| Concern | Where |
|---|---|
| Piece list, art window, type→tint folder, blend softness | `scripts/misc/honeycomb/honeycomb-tuning.js` → `art.cardChrome` |
| Chrome markup (tint stacks + masks) | `scripts/misc/honeycomb/honeycomb-ui.js` → `honeycomb.ui.cardChrome` (called from `honeycomb.ui.card`) |
| Layers, tint wrappers, ink re-seating | `scripts/css/honeycomb.css` → `.hcCardChrome*` block, after `.hcCardFrameBlend` |

- `honeycomb.ui.card` adds `hcCardChrome` to the root for **both layouts** and places the art from
  `cardChrome.windowByLayout[layout]`; it falls back to the placeholder frame only when no chrome is
  tuned. The frame swaps its raster per layout (`frame_gold_horizontal` / `frame_gold_vertical`), and
  `bg` is horizontal-only (a vertical card shows its art there and lays a dark wash instead).
- Ink re-seats onto the chrome's own rectangles: the cost number and owner portrait drop into the coin
  wells (inner hole 62.3%, centre 49.9% / 51.7%), the name into the top band, the supertype row onto
  the ribbon (vertical +2% to 53.5%, ribbon pieces shifted with it), the tags onto the band above the
  emblem (bottom 12.6%), and the rules text on the bench's rectangle (top 61.2%, height 21.2%).
- **Parity with the bench.** `textFit.fitCount` is calibrated to that shorter rules box (30, was 42);
  the same 69-character sample now sets at 18.68px vs the bench's 18.14px. The supertype row matches
  the bench's modes: a SINGLE type prints icon + word, TWO OR MORE print **icons alone**.
- **Owner class glyph.** The winged emblem's glyph comes from the owner's character `artFolder`
  (`classGlyphPathByArtFolder`: knight / priest / lancer so far) via `honeycomb.cardClassGlyphPath`;
  a class Noodle has not drawn yet (necro, vamp, seer) draws no glyph — the intended state, not a hole.
  A card with no owner (an enemy move) draws none either.
- **Shift arrow.** The front/back arrow over the art is helper ink, restyled for the chrome: a small
  gold chevron on a faint dark halo instead of the old dark pill, which read as a play button on the
  gold frame.
- Reduced effects drops the extra blend layers but keeps the primary type's colour.

Two gotchas worth keeping in mind: `cardChrome` window fields must use the `window*Percent` names
`art.cardFrame.*` uses, and a boxed piece needs `height:auto` (the tint wrapper otherwise pins
`height:100%` and stretches the coin rings into ovals).

### Bench parity (session 23)

The bench is meant to predict the live card, so every CSS-driven value it drew is copied to the chrome
(measured element-by-element against both). Now matching:

| Element | Value |
|---|---|
| Tag banner | top 83.2%, height 4.2%, `norwester` 8.6u, letter-spacing 0.1em, padding 0.02/0.5/0.05em, bevel clip-path, light word |
| Gem | `scale(0.56)`, origin 49.95% / 11.95% |
| Ribbon / emblem shadows | the bench's drop shadows; emblem also `scale(0.85)` |
| Supertype glyph | 13.8u (18u on medium) + hard drop shadow |
| Art | `object-position: center 18%` for a party card's bust; an ENEMY move (a full-body sprite chain, figure at its foot) anchors `center bottom` — the 18% landed on the empty top and blanked every enemy card |
| Rules text | side padding `0 0.4em`; box + `textFit.fitCount` as above |
| Name / cost | `#efe4cf` (`--hc-cream`) / `#f0d89a` (`--hc-gold-bright`) — the LIVE palette; the bench was updated to these, not the reverse (Noodle preferred them) |

**Deliberate keeps (not differences):** the tag FILL takes the school's own colour (the bench samples
one school's rose); the card text-shadow is the game's global three-layer recipe (line 147), which the
bench simplified to two layers; the card aspect is the live frame's 1992/2540 (0.03% off the bench's
1176/1500); the art element keeps its dark panel behind the rasters.

**Still the supertype-text handoff** (Claude): a single type prints a straight word + icon where the
bench curves an SVG label along the ribbon; multi-type glyphs are centred where the bench spaces them
at 40% / 60% with the ribbon's tilt. Both are type-setting, not chrome.

## OPEN PROBLEM — supertype text (handoff)

The next big gap, and the blocker to wiring in. Two places, both weak against an otherwise 8–10/10
bench card:

1. **Bench single-mode ribbon label** (`typeMode: single`) — the SVG `textPath` "DAMAGE" on the
   ribbon. Noodle: ~**2/10**. This is the immediate problem.
2. **Live game supertype row** (`honeycomb.ui.cardSupertypeRow`, `.hcCardSupertypeRow`, icon + word
   under the art window) — Noodle: ~**4/10**.

Whoever takes this: it is a type-setting/layout problem, not a chrome problem. Note the BRIEF's page
that "Typography matches the live cards" and the supertype row spec (`9.45 * u`, uppercase,
letter-spacing 0.1em, icon 1.35em). Prior attempt: a words+icons row on the ribbon was reverted
("looks awful, does not fit"); icons-only is the current multi-mode.
