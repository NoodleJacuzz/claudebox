## Rules this pipeline must not break

- **Codenames in every file name, folder and key**; the in-game name appears only in display text.
- **No invented tags.** A missing word goes into the real dictionaries; a tag the model does not know is an arbitrary adjective.
- **Banned:** tan lines, mud, wax, ice, love potion, inflation, hypnosis, objectification. Downblouse and armpit peek only when sure.
- **Clemence is blind and both she and Cinder always have their eyes obscured**; Clemence's cover must be something that can burn away.
- **Spread beats polish in an outfit round.** Two stark, half-wrong designs are worth more than two that look alike.
- **A generated document cannot hold feedback.** `OUTFITS.md` is rebuilt wholesale; his notes live in the generator.
- **Never run the placeholder generator without a copy of `v13 spire images`.** Delete a folder's claimed lines as its real art lands.
- **Common enemies: two images.** Hit and hurt states are engine effects and VFX, not art.
- **Nothing writes into `v13 spire images/_source/cards/`**, and chrome work makes no gameplay change.

> It seems like we need some kind of better universal solution to deal with #2 for making future work

### B39. Re-running the placeholder generator would overwrite real art in 26 folders ☆ — FOUND SESSION 51

Not reported by anyone. Found while measuring B38, and worth fixing before it costs a drawing.

`generate-placeholder-art.py` protects real art with the manifest rule, and the manifest file says so in
its own header: *"Replacing a placeholder with real art? Delete its line below and it is never
overwritten."* The rule in code is `if FORCE is False and name in existing and name not in claimed` —
a file **named** in the manifest is overwritten, a file not named in it is kept.

**Twenty-six enemy folders still list `1-combat.webp` and `1-offense.webp` as claimed.** For the eleven
in B38 that is correct — those files really are the generator's. The hazard is that the manifest is the
only thing standing between a rerun and the art, and nothing checks that it agrees with what is on disk.

Two things worth doing, neither of them urgent and neither of them a design question:

- Have the suite assert that no folder claims a file that is demonstrably a hand-drawn asset. There is
  no marker for that today, which is the actual gap.
- Delete the claimed lines as each enemy's real drawing lands, which is what the header asks for and
  what the 2026-09-21 pass did by accident — those twenty-three folders have no manifest at all.

**A related thing that looks like a bug and is not.** The twenty-three newly drawn enemies have
`1-combat.webp` and no `1-offense.webp`. That is deliberate: the generator's own note says *"An enemy
whose `1-combat` is real art gets NO generated files beside it"*, because a generated attack pose cut
from the old stand-in would turn the enemy into a different creature every time it attacked. The game
falls back to `1-combat` for the attack. What is owed is twenty-three real attack drawings, not a
generator run.

**Confirmed by accident, 2026-09-24.** A session ran `generate-placeholder-art.py` by mistake (it has
no `--help`; asking for one runs it) and it rewrote 396 webp files. 369 came out byte-for-byte the
same size, but 27 did not, and they were real work: `map/preview-shop` was flattened from an 85KB
picture to a 2KB placeholder; the twelve `cards/art/*-broken` and `*-broken-tall` pictures fell back to
the plain recipe; and thirteen enemy poses (`capBrute`, `drownedSalvager`, `gardener`, `gloomWisp`,
`hollowChampion`, `hollowKnight`, `matriarch`, `moldLeech`, `sage`, `shield`) were redrawn. All 26 were
put back from the 2026-09-21 snapshot at `D:\syrup-town13 spire images`, each matching the size
recorded minutes before the run. The one that could not be (`characters/priest/ecstatic/recover`) is on

**Until this item is fixed, do not run the generator without first copying `v13 spire images`.**

### P27. Enemies turn around while attacking ☆ — TRACED SESSION 55, AND IT IS THE DRAWINGS

> Enemies turn around while attacking sometimes

**It is not the mirror, and it is not the animation. Both were checked and both are innocent.**

1. **The mirror is switched on but nothing opts into it.** `honeycomb.art.spriteFlipped` only flips a
   fighter whose definition carries `sideFacingArt: true` AND who is standing on the side it does not
   belong to. Counted across every enemy and every character: **zero carry `sideFacingArt`.** So the
   flip can never fire, and the `hcMirrored` class is never added.
2. **The acting animation does not flip either.** `.hcActing` is `translateY` plus `scale(1.04)`, and
   `.hcLunge` is a `translateX`. Neither has a `scaleX`, so nothing in the CSS turns a fighter round.
